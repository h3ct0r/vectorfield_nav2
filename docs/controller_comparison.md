# Controller comparison

:::{note}
Generated by `vectorfield_system_tests/benchmarks/compare_controllers.py` from a recorded run (2026-10-19). The numbers are informative and do not gate CI.
:::

The M3 route on Nav2's loopback simulator, driven 5 times by each controller with identical limits, goal checker, velocity smoother and collision monitor.

## Setup

- ROS 2 Jazzy, Nav2 1.3.13; `loopback_demo.launch.py`, map `open_10x10`, motion model `differential`, headless.
- Hardware: Linux aarch64, 12 CPUs.
- Route: from (0, 0, 0°), NavigateToPose to (3, 0, 0°), (3, 3, 90°), (0, 3, 180°) in turn (map x, y, yaw), each goal within 120 s of simulated time. A route is completed when all three goals succeed; a run stops at its first failed goal.
- One launch per controller and run; runs interleaved (each run cycles through Vector field, Regulated Pure Pursuit, MPPI, Graceful).
- Controller: `controller_frequency` 20 Hz; goal checker `nav2_controller::SimpleGoalChecker` (`xy_goal_tolerance` 0.25 m, `yaw_goal_tolerance` 0.25 rad, `stateful` True); progress checker `nav2_controller::SimpleProgressChecker` (`required_movement_radius` 0.5 m, `movement_time_allowance` 10 s).
- Velocity smoother (`cmd_vel_nav` to `cmd_vel_smoothed`): `max_velocity` [0.5, 0.0, 2.0], `max_accel` [2.5, 0.0, 3.2], `max_decel` [-2.5, 0.0, -3.2], `scale_velocities` True; then the stock collision monitor (`cmd_vel_smoothed` to `cmd_vel`).

### Shared limits

- Forward speed (m/s): 0.4
- Yaw rate (rad/s): 1.5
- Linear acceleration and deceleration (m/s²): 1.0
- Angular acceleration (rad/s²): 3.2

### Controller parameters

Each run replaces `controller_server.FollowPath` with the block below; everything not listed keeps its stock value. RPP and Graceful have no linear acceleration parameter, and Graceful no angular acceleration parameter: for them those limits come only from the shared velocity smoother.

- **Vector field**: FollowPath of vectorfield_bringup `config/controller/differential.yaml`, with `desired_speed: 0.4`, `max_linear_vel: 0.4`, `max_angular_vel: 1.5`, `max_linear_accel: 1.0`, `max_linear_decel: 1.0`, `max_angular_accel: 3.2`.
- **Regulated Pure Pursuit**: the plugin defaults (`nav2_params.yaml` has no RPP block), with `desired_linear_vel: 0.4`, `rotate_to_heading_angular_vel: 1.5`, `max_angular_accel: 3.2`.
- **MPPI**: FollowPath of nav2_bringup `params/nav2_params.yaml`, with `vx_max: 0.4`, `wz_max: 1.5`, `ax_max: 1.0`, `ax_min: -1.0`, `az_max: 3.2`.
- **Graceful**: the plugin defaults (`nav2_params.yaml` has no Graceful block), with `v_linear_max: 0.4`, `v_angular_max: 1.5`.

### Metrics

- Cross-track error: distance from the true position (map → base_footprint; the loopback simulator localizes perfectly) to the first global plan published on `/plan` for the goal, from goal send to the result. RMS over the pose samples (uniform in time, so in-place rotations count as zero-error samples) and maximum, pooled over the route.
- Time to goal: simulated time from sending the goal to SUCCEEDED, summed over the three goals (the loopback simulator publishes `/clock` at 10 Hz, so times are multiples of 0.1 s).
- RMS jerk: second finite differences of the commanded linear (x) and angular (z) velocity, pooled over the route, for the controller output (`cmd_vel_nav`) and for the final command after the shared smoother and collision monitor (`cmd_vel`). Commands received less than 20 ms apart count as one update (the last one, which the robot keeps; the controller server occasionally publishes two back to back when its loop catches up), and the finite-difference step is the median interval between updates. Measured median interval between updates, per route: `cmd_vel_nav` 50 ms, `cmd_vel` 50 ms.

## Interpretation

- Cross-track RMS, lowest to highest mean: MPPI 0.042 m, Vector field 0.048 m, Regulated Pure Pursuit 0.070 m.
- Cross-track max, lowest to highest mean: Vector field 0.097 m, MPPI 0.099 m, Regulated Pure Pursuit 0.134 m.
- Time to goal, lowest to highest mean: Vector field 24.2 s, Regulated Pure Pursuit 25.2 s, MPPI 31.6 s.
- Linear jerk of the controller output, lowest to highest mean: MPPI 7.91 m/s³, Regulated Pure Pursuit 10.38 m/s³, Vector field 12.12 m/s³.
- Angular jerk of the controller output, lowest to highest mean: MPPI 3.52 rad/s³, Regulated Pure Pursuit 36.76 rad/s³, Vector field 48.27 rad/s³.
- Regulated Pure Pursuit completed 4 of 5 routes. Its 1 failed run ended at goal 1 with status UNKNOWN (timed out), a closest approach to the goal of 0.000 m (`xy_goal_tolerance` 0.25 m), 0 reversals of an in-place rotation command; the first warning or error logged after the goal was sent was most often `collision_monitor: Robot to stop due to invalid source. Either due to data not published yet, or to lack of new data received within the sensor timeout, or if impossible to transform data to base frame`.
- Graceful completed 0 of 5 routes. Its 5 failed runs ended at goal 1 with status UNKNOWN (timed out), a closest approach to the goal of 0.251 to 0.254 m (`xy_goal_tolerance` 0.25 m), 348 to 457 reversals of an in-place rotation command; the first warning or error logged after the goal was sent was most often `controller_server: Failed to make progress`. The robot stopped translating just outside the goal tolerance and only rotated, so the goal checker never accepted the pose; the progress checker aborted FollowPath and the behavior tree's recoveries retried until the goal timeout.

Caveats. The loopback simulator applies the final command exactly, without dynamics, noise or localization error, on an empty map, so the numbers compare the control laws under ideal conditions and say little about a real robot. Each route segment is a straight plan; most of the cross-track error comes from how a controller turns onto a segment whose direction is 90° from the robot's heading (goals 2 and 3) and how it approaches the goal. The vector-field controller steers a control point 0.2 m ahead of `base_footprint` (differential model), while the error is measured at `base_footprint` for every controller. Jerk of the controller output reflects how each controller limits its own acceleration; RPP and Graceful rely on the shared smoother for the linear acceleration, which the `cmd_vel` table includes. MPPI samples random trajectories, so its runs are not deterministic.

The loopback simulator's clock also shapes the controller outputs. It publishes `/clock` at 10 Hz while the controller server calls the controllers about every 50 ms, so every other call sees no elapsed simulated time. The vector-field controller then returns its previous command, so its acceleration limits hold in simulated time and its output changes once per 0.1 s tick. Finite differences of such a staircase raise the jerk of `cmd_vel_nav` compared with an output that also changes between ticks; the `cmd_vel` table, after the shared smoother, compares the commands the robot receives.

## Reproducing

In the Jazzy development container (or any Jazzy or later workspace):

```bash
rosdep install --from-paths src --ignore-src -y
colcon build --packages-up-to vectorfield_system_tests
source install/setup.bash
ros2 run vectorfield_system_tests compare_controllers.py --runs 5 \
  --out-md controller_comparison.md --out-csv controller_comparison.csv
```

`--controllers vf,rpp` restricts the set; `--from-csv` regenerates the page from a recorded CSV; `--log-dir` keeps each launch's output. A run that fails for a Nav2 reason outside the controller plugin is repeated up to `--retries` times (default 2) and listed separately. One run takes about one minute. The recorded run took 30 minutes of wall time.
